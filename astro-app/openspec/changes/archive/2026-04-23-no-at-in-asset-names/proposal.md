## Why

Production builds emit CSS chunks containing `@` characters in the filename
(e.g. `_astro/index@_@astro.pYfenLRC.css`, `about@_@astro.KPW2n5Ex.css`). The
WHO deployment environment sits behind a WAF that rejects requests whose paths
contain `@`, so these assets 404 in production even though they load fine
locally. We need to guarantee that no emitted asset path contains `@`.

## What Changes

- Override Vite's rollup asset filename pattern so emitted CSS/JS/asset
  chunks do not contain `@` (the `@_@` substring comes from Astro's virtual
  module IDs like `index.astro?astro&type=style` being sanitized by Rollup's
  default `sanitizeFileName`).
- Verify the production build (`yarn build`) produces zero files under
  `dist/` matching `*@*`, and that generated HTML/CSS references agree.
- Add a lightweight build-time guard (post-build check or unit test) that
  fails the build if any emitted asset path still contains `@`, so this
  cannot regress silently.

## Capabilities

### New Capabilities
- `asset-naming`: rules for how production build artifacts are named, with
  explicit forbidden-character constraints driven by WAF compatibility.

### Modified Capabilities
<!-- none -->

## Impact

- Affected code: `astro.config.mjs` (Vite `build.rollupOptions.output`
  config); possibly a new script under `astro-app/scripts/` or a vitest
  check referenced by the build pipeline.
- Affected output: contents of `dist/_astro/` — filenames change, but
  hashed content is unchanged. HTML references to those assets are
  regenerated by the same build, so no manual sync is needed.
- No runtime behavior change; no new dependencies.
- Rollback: revert the config change — filenames return to the current
  `@_@` pattern, which still works outside the WAF.
